# Work plan: branch-scoped working memory

**The branch is the unit of work. One committed plan per branch is its memory.**
The plan holds volatile state: what we are doing and where we stopped. Durable
truth lives in the docs `rjv-spec-driven` owns: spec in `_docs/features/`,
glossary in `CONTEXT.md`, ADRs in `docs/adr/`. The plan links to durable docs
and never copies them.

- `.plans/<name>.md` is the working memory for one branch. It is committed, so
  any agent on any machine that checks out the branch resumes from it.
- **Each plan declares `Branch: <name>` in its header.** The filename can be any
  readable topic name. Resume finds the plan whose `Branch:` matches
  `git branch --show-current`. Git branches are the active-work index: there is
  no `RESUME.md` or other index file. Concurrent work runs on concurrent branches
  (or worktrees), each with its own committed plan.
- **A plan is never deleted.** It is archived on merge and kept. It moves to `.plans/shipped/` with a
  final status and dates. Top-level `.plans/*.md` is work in flight;
  `.plans/shipped/` is the delivery record. The lifecycle continues past merge
  into maintenance; see [`LIFECYCLE.md`](./LIFECYCLE.md).

The same files serve Claude Code, Codex and any other agent. Reference this
skill from AGENTS.md so every agent follows it.

## Authorship: the human's identity only

**Leave AI authorship and generator credit out of everything you write, unless
the human explicitly asks for it.** That covers commit messages and trailers,
PR/issue bodies, comments, plans, specs, ADRs, source comments and generated
files. It excludes `Generated by Claude`, `Generated by Codex`, an AI
`Co-Authored-By`, model names, badges, emojis and any equivalent signature or
footer. Git already records the human author. Keep any attribution a human
deliberately wrote exactly as written.

## Entry point: resume or start

On any new conversation about the current work, walk these steps in order.
Write no code before step 4 is done.

1. Find this branch's plan:
   ```
   b=$(git branch --show-current)
   grep -l "^Branch: $b\$" .plans/*.md
   ```
   - **1 match**: that is the plan.
   - **0 matches**: the branch is not scoped yet. Classify it with the
     Build-mode gate below. `simple`: write no plan file; the commit message
     carries the one-line intent. Steps 2 to 5 do not apply. Otherwise create a
     plan (format below) with `Branch:`, goal and `Started:` before touching code. For a follow-up
     on shipped work, first run `grep -l "<topic>" .plans/shipped/*.md` and link
     that plan.
   - **More than 1 match**: this breaks one plan per branch. Ask the human, or
     take the most recently modified plan and flag the others as stragglers.
2. `grep -A6 ">>> RESUME HERE <<<" <that-plan>` to land on the resume block,
   then read the whole plan.
3. Read every durable doc the plan's **Source of Truth** section links (specs
   via `rjv-spec-driven`, glossary, ADRs).
4. **Reconcile-on-open** (below). Only then act.
5. Report to the human: current state, drift found, next step about to be taken.

Done when: on a `simple` branch, the commit message carries the intent;
otherwise `Last reconciled:` carries today's date and the human has the step 5
report.

## Plan format

```
# Plan: <topic or branch>
Branch: <branch-name>          ← the deterministic key; resume matches on this line
Build mode: simple | spec-driven | gated + spec-driven
Status: brainstorm | approved | in-progress | blocked | shipped | maintenance | closed
Started: <date>                ← stamped at creation
Shipped: <date | —>            ← stamped when it lands on main / hits prod
Last reconciled: <date> — <matches reality? what drifted?>

## Goal            ← what this branch delivers
## Cast            ← who builds this: agents, models, approver (see below)
## Decisions       ← locked choices + why (crystallized brainstorm; promote hard ones to ADRs)
## Open Questions  ← still-live brainstorm (resolve → Decisions or ADR)
## Current State   ← VERIFIED ground truth now
## Next Steps      ← ordered resume point; carries the RESUME HERE block
## Regression Guard← how to avoid breaking existing behaviour
## Out of Scope
## Source of Truth ← links to _docs/ spec, glossary, ADRs, key file:line
```

Task lists, test cases and data models go under Next Steps or Current State.
Write one line per item in agent register: terse facts, file:line. The plan
holds only volatile state; settled durable facts promote out in real time
(below).

**Brainstorm lives in the plan.** A resolved point becomes a one-line Decision
with its why (promote hard-to-reverse ones to an ADR). An unresolved point goes
to Open Questions. Any other musing becomes one of those two or is deleted.

**Status is the lifecycle, and it runs past merge:**

```
brainstorm → approved → in-progress ⇄ blocked → shipped → maintenance → closed
```

`shipped` = merged and live. `maintenance` = live and being watched: hotfixes,
follow-ups and prod findings land against it. `closed` = settled, nothing
outstanding, read-only history. **The status is true at all times.** Stamp it
in the same commit as the event; a stale `in-progress` on a merged plan
corrupts the timeline.

**Next Steps always carries the literal marker block:**

```
## Next Steps
>>> RESUME HERE <<<
Step: <plan step id> — <status>
Criteria: <active criterion IDs | none>
Do next: <one imperative — the exact next action>
Must-read first: <file:line, …>
<<< END RESUME >>>
1. …ordered steps after the current one…
```

Copy `>>> RESUME HERE <<<` and `<<< END RESUME >>>` byte for byte. The resume
grep matches the literal strings, so a fixed marker lands every time even when
headers drift. Rewrite the block at the end of every step.

Text after `←` is annotation. The `Branch:` line holds the name and nothing
after it, or the resume grep misses the plan.

**Cast section.** The agent lineup is a locked decision, recorded at plan
creation. Every resume plays its role without renegotiating:

```
## Cast
Orchestrator: claude-code @ fable        ← holds this plan, integrates
Author:       claude (main session)      ← or: codex · qwen3.6:35b via rjv-codex-ollama-subagents
Reviewer:     codex via codex:rescue     ← explicit APPROVED gates each step (gated builds)
Subagents:    haiku = sweeps/forwarders · sonnet = routine code   ← picked per task via rjv-subagents-claude
Human gates:  spec sign-off · USER-flagged decisions · live/prod switches
```

**Every task on every branch is routed by `rjv-subagents-claude` (Codex:
`rjv-subagents-codex`).** The Cast is the starting default. When the mix of
work shifts, recast and log it as a Decision with the why. Casting rules for
gated builds live in `rjv-gated-build` (`CASTING.md`).

## Build-mode gate: classify before code

At plan creation and every reconcile, record exactly one `Build mode` by
walking the lists below:

```text
simple
spec-driven
gated + spec-driven
```

Use `spec-driven` when ANY item is true:

- real feature or behaviour change with more than one meaningful implementation slice;
- architecture/foundation, public SDK/API/contract, state machine, durable data, or migration;
- multiple apps, actors, journeys, providers, callbacks, jobs, or embedded Features;
- the branch needs acceptance criteria, a glossary, or a hard decision record;
- a review discovers that prose intent and implementation can diverge.

Use `gated + spec-driven` when ANY item is true:

- money, financial correctness, production safety, security, destructive work, or high blast radius;
- multiple author/reviewer agents or an explicit independent approval loop;
- zero-debt, human QA, or phase-by-phase ship gates;
- repeated rejection/rework shows one agent's self-review is insufficient.

`simple` is only for one-slice, low-risk work whose complete intent fits in one
plan sentence. When unsure, choose the stricter mode. **A branch keeps the
strictest mode it has qualified for**, even when that mode's gate is
inconvenient.

Mode consequences:

- `simple` → no plan file and no spec. If the branch later qualifies for a
  stricter mode, create the plan then.
- `spec-driven` → load `rjv-spec-driven`; create/link the durable spec before `WORK`.
- `gated + spec-driven` → also load `rjv-gated-build`; grill the spec before code and
  require independent approval per slice.
- In both spec modes, the plan's `RESUME HERE` names the active criterion IDs.

## Ceiling: the plan stays thin

**Hard ceiling ~400 lines / ~20KB.** A plan is re-read on every resume, so its
size is a token cost paid again every turn. This skill owns the number;
`rjv-gated-build` (`ANCHOR-DOC.md`) holds the measured failure behind it.

- Git holds history: `git log .plans/<name>.md` is the log. The plan is a
  current-state surface.
- Real-time promotion (below) drains settled facts continuously.
- Over the ceiling at reconcile → promote durable facts to their durable home
  (`rjv-spec-driven`) and compress BEFORE acting.

## Real-time promotion

Write each settled fact to its durable home the moment it settles. Promoted
docs are branch commits, so they travel through the same PR and land on `main`
with the code.

`rjv-spec-driven` owns the rest: which facts leave, where each one goes, the
mutation test that decides plan state from durable truth, and the artifact
formats (spec / glossary / ADR). Load it before promoting anything.

## Reconcile-on-open

```
read plan → VERIFY each "done" claim against real code/db/tests →
(spec modes) regenerate the spec status block from a fresh suite run
(`rjv-spec-driven`) → note drift in Current State → rewrite Next Steps →
stamp Last reconciled →
if over the ~400-line ceiling, promote + compress → then act
```

A "done" you have not verified is a rumor; verify every one.
**During work:** update the plan in the same turn as the change.
**On stop/handoff:** rewrite the `>>> RESUME HERE <<<` block to the exact resume
point, and mark `done` only what is verified.

## Plan vocabulary stays in the plan

`Step: <id>`, `Status: shipped`, `RESUME HERE`, `.plans/shipped/…` and criterion
IDs are the file's nouns. The user does not have the plan open and is not
tracking step numbers.

When reporting in chat, say what the step is and what state it is in: "the old
components were never deleted" (instead of "step 6 is open"). Cite the plan
path once, at the end, and only if they would need to open it.

## Merge, maintenance, timeline, roadmap → `LIFECYCLE.md`

On merge, archive the plan: `git mv .plans/<name>.md
.plans/shipped/<YYYY-MM-DD>-<name>.md`, status stamped in the same commit. Read
[`LIFECYCLE.md`](./LIFECYCLE.md) when a branch is landing, when work arrives
against something already live, or when someone asks what shipped and when. It
holds the merge ritual, the CI-guardable invariants, the maintenance phase, how
to read the delivery timeline back, and the durable roadmap.

## With rjv-spec-driven and rjv-gated-build

- **`rjv-spec-driven`**: mandatory for `Build mode: spec-driven` and
  `gated + spec-driven`. It owns the durable acceptance criteria, glossary, and ADRs.
  `WORK`, handoff, review, and QA refer to permanent criterion IDs.
- **`rjv-gated-build`**: mandatory for `Build mode: gated + spec-driven`. The plan
  is the compressed operational anchor: cast, active criterion IDs, evidence, grill
  trail, tombstones, and resume point. Durable acceptance criteria stay in `spec.md`.
  Multiple concurrent gated builds remain separate branches/plans.
